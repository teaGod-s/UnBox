# UnBox 无头浏览器反爬插件（Moli）—— 设计评估

> 状态：**评估 / 待立项（非实现 spec）**。本文记录「用跨平台无头浏览器插件解决
> 站点侧 JS 渲染/加密反爬」的可行性、方案分层、风险收益与建议。是否立项由
> 份额需求驱动，当前无明确高频刚需，故按「评估文档」留存。

## 1. 背景与动机

UnBox 采用「纯 Go 规则引擎」架构（M6/M7/M6.2），不执行宿主 JAR、不内嵌浏览器。
绝大多数 TVBox 站点可由 XBPQ / XYQHiker / CMS / drpy2 静态解析覆盖。但实际排查
（2026-11-08 主订阅冒烟，149 站）发现有少量站点属于**站点侧反爬**，无法被静态引擎
覆盖：

| 反爬类型 | 例 | 能否静态解决 |
|---|---|---|
| MacPlayer 明文 m3u8（带 `\/` 转义） | 某影视站 | ✅ 已修（macPlayerURL 解码） |
| 加密云播（url 密文 + 第三方解析 + 混淆 JS） | 某加密源 某云播源 | ❌ 需执行 JS 运行时 |
| 站点对出口 IP 封禁 / Cloudflare 522/403 | 某站点电影 | ❌ 与浏览器无关，IP 级 |
| 平台页（B站/腾讯… 需会员） | 数个 | ❌ 业务侧无解 |

用户提出：能否像 TVBox 生态那样提供「无头浏览器插件下载」能力（Moli/墨筂 等），
解决这批 JS 渲染型反爬站点。

## 2. Moli 是什么

Moli（曾用名墨筂/MoliSpider/JSU）是 TVBox 社区常用的**跨平台无头浏览器**：

- 基于定制 Chromium，体积约 100–300 MB 随宿主分发；
- 暴露本地 HTTP API（约 `127.0.0.1:<port>`），TVBox 的 JAR 通过它执行页面 JS
  （`moli://...` / 本地代理协议）；
- 能力：打开页面、执行脚本、（模拟）等待渲染完成、取回页面 JS 变量的值。

它解决的正是「真实播放地址由页面 `<script>` 动态生成」这类问题——浏览器执行
到哪一步，它就能取到哪一步的结果。

## 3. 方案分层（按投入/收益）

### A. 明确报错层（已完成/收尾中）

不引入运行时，把反爬/加密源从「误导性的『未找到真实播放地址』」改成明确原因：

- ✅ 加密云播源（某云播源/某云播源）→「该线路为加密云播源，需浏览器/第三方解析，
  UnBox 无法直接播放」（rule/xbpq `cipherCloudFrom` 已提交 `5caa6b9a`）
- ✅ 平台页（B站/腾讯…）→「需平台会员或解析服务」（resolver `platformPageName`）
- ➕ HTTP 522/403/5xx →「站点反爬或源站异常：探测播放地址返回 HTTP xxx（可换线路
  或稍后重试）」（本文提交）

成本低、收益是「用户不再误以为 bug」，但**不实际让反爬站能播**。

### B. 轻量 JS 执行桥（可评估）

不引 Chromium，仅对**单文件、无 DOM 依赖**的混淆 JS 用 goja（项目已依赖）执行：

- 适用：`player_aaaa.url` 密文 → 简单 AES/base64/字符表解密 → m3u8；
- 不适用：需要真实 DOM（`document.getElementById`、`new Image`、事件回调）的脚本
  ——那本质上要浏览器。

评估结论：**多数加密云播依赖第三方接口 + DOM 时序，B 只能覆盖少量「纯算法解密」**
的脚本。收益不确定，需先对存量加密站点做脚本形态普查（约 n 个）再定。

### C. Moli 无头浏览器插件（真正立项才是它）

四子系统：

1. **插件下载器**：按平台下载 Moli 分发二进制（Windows x64 / macOS arm64 / Linux x64）
   到用户数据目录，校验 SHA-256，版本管理；下载源需固定且持续（TVBox 社区分发源
   常漂移，GitHub raw 也被限流过）。
2. **进程管理器**：按需启停 Moli 本地服务，随应用生命周期；
3. **JS 执行桥**：对 hits「JS 渲染型反爬」的站点，走 Moli 渲染取真实源，复用现有
   `Resolve` 链路最外层；
4. **安全边界**：本地执行任意站点 JS，需考虑权限隔离、控件层提示、下载源固定。

成本与风险：

| 项 | 评估 |
|---|---|
| 工作量 | ≈ M8 网盘子系统的量级（数周） |
| 体积 | 用户首次按需下载 100–300MB；分发源漂移风险 |
| 收益 | 覆盖 JS 渲染型（某加密源 某云播源 等）；**不解决 IP 级封禁**（某站点 522 这类） |
| 架构影响 | 与 M6「纯 Go、零下载、零执行第三方代码」哲学相抵触；引入本地浏览器运行时 |

**关键边界**：Moli 只能解决「浏览器能播但静态解析不出」的 JS 渲染型；IP 级封锁、
平台会员、站点下线是无头浏览器也无解的（某站点 522 即此例，换 IP/网络才能解）。

## 4. 决策建议

1. **补完 A**（本文已改）：反爬/加密源明确报错，用户有数；
2. **B 立项前做一次加密站点脚本形态普查**：统计存量 XYQHiker/XBPQ 站点里
   `player_aaaa.url` 密文 + `from` 的分布，若多数是纯算法解密 → B 性价比高；
   若多数是 DOM/第三方接口 → 放弃 B。
3. **C（Moli）暂不立项**：当前反爬站占比低（149 站冒烟中约 3–5 个）、C 量大、且
   与架构哲学冲突、IP 级问题无解。留待「需 JS 渲染的站点占比明显上升」或用户
   明确要求时按本评估立项。

## 5. 非目标

- 不把 Moli 做成默认安装/内置依赖；
- 不解决 IP 级封禁（522/403 属网络环境，提示换线路）；
- 不逆向/绕开站点故意收费的会员墙（那不是反爬是业务）。
